Спецификация: [spec.md](spec.md). Здесь — решения оператора, принятые после неё. При расхождении действует этот файл.

## 2026-10-23 — Поиск возможностей вместо поиска дефектов

**Решение оператора** (план «Client Hunter — Updated Development Plan», одобрен 2026-10-23).

### 1. Юрлицо больше не фильтр
- Раньше (спека 3.1, 5.4, 8.6): сайт без признаков юрлица или с признаками ИП → `rejected_auto` (`entity_unknown`, `entity_sole_trader`).
- Теперь: тип юрлица определяется и сохраняется, но **никого не отсеивает**. Анализируются все коммерческие сайты: компании, ИП, независимые специалисты.
- Также больше не отсеивают: `no_verified_observation` (категория B не требует дефектов), `no_contact`, `no_mx`.
- Отсеиваются только сайты, анализ которых невозможен: недоступен, robots.txt, припаркован, редирект на чужой домен, дубликат. Плюс правила сегмента S1 (не Shopify, магазин закрыт).

### 2. Риск контакта — отдельное поле (`outreach_risk`)
- Коммерческая ценность компании и законность холодного письма — **разные вопросы**. Риск хранится отдельно (таблица `outreach_risk`), показывается рядом с компанией и **никогда не влияет на отбор и ранжирование**.
- Классы: `low` / `review_required` / `high`; с причиной, уверенностью, неизвестными и тем, что проверить до контакта.
- Правила — код ([src/outreach/risk.ts](../src/outreach/risk.ts)) + `cold_email_baseline` в профиле рынка. Это рабочая конфигурация, не юридическая консультация.
- `low` не означает гарантированного разрешения. Одобрение оператора не отменяет требований закона.
- Риск определяется правилами рынка и типом получателя, **не наличием email** (правила `2026-10-23.2`). Доступность контакта — отдельное поле `contact_status`: `email` / `form_only` / `phone_or_messenger` / `none`. Для отдельного адреса риск может быть выше, чем для получателя (публичная почта, именной адрес).
- Автоматической отправки нет.

### 3. Контакты
- Собираются все публично указанные на сайте адреса: на домене компании **и публичная почта** (gmail, outlook, ISP). Раньше публичная почта отбрасывалась (`allow_freemail_addresses: false`).
- Публичная почта никогда не даёт `low`: это часто личный ящик (персональные данные по GDPR).
- По-прежнему не собираются служебные адреса: noreply, privacy, dpo, jobs/careers/hr, accounts/invoices, webmaster/postmaster/abuse.
- Поля профиля рынка `allow_freemail_addresses`, `allow_named_business_address` теперь влияют только на риск, не на сбор.
- Кроме email сохраняются другие публичные каналы (таблица `contact_channels`): страница с контактной формой, телефон (ссылки `tel:` и подписанные номера на странице контактов, в шапке и футере), WhatsApp и Telegram (ссылки на чат, не кнопки «поделиться»). Номера из комментариев, отзывов и цитат не собираются. Ничего не отправляется и не заполняется.

### 4. Ограниченная инспекция
- До 6 страниц на сайт; приоритет: главная, о компании, услуги, каталог, контакты, сценарий клиента (заявка/бронь/заказ/цены); юридические — только на оставшиеся места. Статьи блога и новостей не открываются.
- Сохраняется очищенный основной текст страницы (без меню/футера/баннеров, строки, повторяющиеся на разных страницах сайта, убираются) — до `page_main_text_max_chars` — и до `page_links_max` внутренних ссылок.
- Признаки уже имеющихся возможностей сайта (корзина, форма, онлайн-бронь, калькулятор, поиск, цены, личный кабинет, чат, мессенджеры) считаются кодом.
- Каждая проверка — запись в `inspections`; старые страницы и находки не перезаписываются.

### 5. LLM
- Используется **Claude Haiku** (через API, отдельный биллинг) и для отбора, и для глубокого анализа — вместо Sonnet для досье (спека 9.1). Модель меняется в `config/llm.yaml`.

### 6. Сегмент S3
- Новый сегмент: локальные услуги и независимые специалисты (фотографы, салоны, мастерские, школы, архитекторы, консультанты) — [config/segments/s3-local-services.yaml](../config/segments/s3-local-services.yaml).

## 2026-10-24 — Этап C: глубокий анализ и досье

Архитектурные решения Claude Code в рамках плана от 2026-10-23 (задача [#1](https://github.com/DenisLAvrov14/client-hunter/issues/1)); оператор принимает их при ревью PR.

### 1. Что делает этап C
- `npm run deep -- --domain …` — только для явно указанных компаний (короткий список после этапа B), не массово.
- Claude Haiku (`config/llm.yaml`, `stages.deep`) получает тот же очищенный текст сайта, что и этап B, но с большим лимитом, плюс известные внутренние ссылки и доступность контакта.
- Модель может запросить до 3 страниц только из известных внутренних ссылок; код читает их сам с учётом robots.txt и сохраняет как отдельную проверку (`inspections.mode = 'deep_pages'`, `result_status = 'supplement'`). Логика контактов по-прежнему опирается только на последнюю настоящую проверку.

### 2. Доказательства проверяет код, не модель
- Каждое утверждение — `fact` / `inference` / `hypothesis` / `unknown` со ссылками на доказательства: цитата со страницы, находка из `observations`, признак сайта, определённый кодом.
- Цитаты ищутся в тексте страниц, находки — в базе. Непроверяемое доказательство удаляется, утверждение понижается (факт → вывод → гипотеза). Находка `likely` подтверждает только вывод, не факт.
- Цитата должна быть на той странице, которую указала модель (адреса сравниваются без завершающего `/` и `#якоря`). Если цитата найдена на другой странице сайта, адрес исправляется на настоящий, она подтверждает только вывод, не факт, и модель получает просьбу указать верную страницу. Неверный адрес в досье не попадает. То же для этапа B: адрес цитаты исправляется на настоящий.
- Предложение того, что на сайте уже есть, не засчитывается; `pursue` без обоснованного предложения становится `maybe`.

### 3. Черновик письма — только для просмотра
- Черновик проверяется правилами `config/copy-rules.yaml` (язык, режим рынка, без цифр и чужих ссылок, длина, запрещённые фразы). Строку отказа добавляет код, не модель.
- Не прошедший проверку черновик помечается в досье как непригодный. Ничего не отправляется: этап C не обращается к почте.
- В досье риск обращения (`outreach_risk`) показан отдельно от доступности контакта (`contact_status`) и на рекомендацию не влияет.

### 4. Стоимость
- До 4 вызовов на компанию (2 прохода × 2 попытки). Перед каждым вызовом проверяется худший случай против лимитов на запуск и месяц (`config/limits.yaml`).
- Автоматические повторы SDK Anthropic отключены (`maxRetries: 0`, по умолчанию SDK повторяет до 2 раз): один вызов — ровно один HTTP-запрос, и каждый проходит проверку и учёт бюджета. Временные ошибки (429, 5xx, сеть) повторяют сами этапы B и C, каждая попытка учитывается; если API не сообщил расход, записывается худший случай. Параметр `sdk_max_retries` удалён из `config/llm.yaml`.
- Результат кэшируется по хэшу (модель + версия промпта + вход): повторный запуск с теми же данными бесплатен; изменённый промпт получает новую версию автоматически.
- `--dry-run` открывает базу только для чтения: не применяет миграции, не пишет, не вызывает API. Показывает вход первой компании, сколько компаний будет проанализировано и сколько взято из кэша, и оценку: обычную и худшую.

### 5. Доступ к данным
- Риск получателя, риск адресов, доступность контакта и находки читаются через функции `src/db/repo.ts`, одинаково для отчёта кандидатов, отчёта отбора и досье.
- Строки риска по старым правилам `2026-10-23.1` (там строка без контакта означала «email не найден») не показываются как риск получателя; версия хранится в одной константе рядом с `RISK_RULES_VERSION`.

## 2026-10-24 — Этап C после первого платного запуска (5 компаний)

Первый запуск (6 вызовов, $0.0226) показал ошибки качества. Решения Claude Code; оператор принимает их при ревью PR #2.

### 1. Признаки сайта — по ключу
- Во входе модели каждый признак показан с ключом: `- cart_checkout · online shop / cart: yes (…)`. Раньше показывалось только описание, а проверка ждала ключ, поэтому все утверждения «на сайте уже есть…» понижались до гипотез.
- Код принимает ключ или точное описание из входа; придуманные ключи (`online_shop`) не угадываются и считаются непроверяемыми.
- В разделе «Что уже есть на сайте» признак, которого код не нашёл, не подтверждает утверждение даже как вывод. В остальных разделах «на сайте нет X» по-прежнему только вывод (код может пропустить виджет).
- Предложение того, что код уже нашёл на сайте, не засчитывается и при `already_exists: unknown`.
- Текст страницы для детекторов больше не склеивает соседние элементы («in-personSign in» → «in-person Sign in»): вход в кабинет, онлайн-запись и т. п. на таких сайтах раньше не находились. Действует для новых проверок.

### 2. Черновик опирается на доказательства
- Модель указывает, о каком предложении письмо (`opportunity_index`, должно совпадать с выбранным), на каком наблюдении из него оно строится (`observation_index`) и как подано (`framing`: наблюдение или вопрос).
- Факт можно назвать как наблюдение; вывод — только спросить («не нашёл на сайте…, верно ли…?»); гипотеза — не основание для письма. Нарушение — повторная попытка, а после неё черновик помечается непригодным с причиной. Черновик при «не предлагать» тоже помечается.
- Остающееся ограничение: код проверяет заявленную основу письма, но не каждое предложение текста; лишние утверждения в теле письма запрещены промптом, не кодом. Поэтому черновик всегда читает человек.

### 3. Калибровка рекомендации
- Все пять ответов были «возможно» из-за неизвестных объёмов заказов. В промпте теперь критерии: `pursue` — лучшее предложение опирается на факт, важно для бизнеса, его нет на сайте, проект реалистичен; неизвестные внутренние показатели не мешают. `maybe` — только выводы, неясная значимость или неясно, есть ли сама проблема. `drop` — ничего не подтверждено, уже есть или не наш клиент.
- Код только понижает: `pursue` без факта в основе лучшего предложения → `maybe`. Повышать до `pursue` код не может.

### 4. Мелкие исправления
- Оценка «обычной» стоимости в `--dry-run` — 5 500 выходных токенов на компанию (было 3 000; в первом запуске 4,5–7,4 тыс.). Худший случай по-прежнему считается по `max_output_tokens`.
- Форма обращения, которая есть на многих страницах, в отчётах показана одной строкой (страница контактов первой); данные в базе не меняются.
- В досье значения на английском (`partially`, `form_only`, `offer`) заменены русскими; технический журнал проверки помечен как английский. Английские служебные слова в русском тексте модели («how часто») — повод для повторной попытки.
- Дополнительные страницы: из известных ссылок убраны служебные адреса Cloudflare (`/cdn-cgi/`, защита email от сбора — не запрашивается) и файлы (PDF и т. п., их читатель страниц всё равно пропускает). Страницы, прочитанные почти без текста, явно названы во входе — их подстраницы хорошие кандидаты. Логика запроса страниц не менялась.

## 2026-10-24 — Этап C после второго платного запуска

Второй запуск (8 вызовов, $0.0358): 4 досье из 5, ошибок проверки 0. Исправлено то, что он показал. Решения Claude Code; оператор принимает их при ревью PR #2.

### 1. Обрезанные ответы
- A1 Designs дважды упёрлась в 8 000 выходных токенов. SDK падал на разборе неполного JSON раньше, чем код видел `stop_reason`, поэтому ошибка считалась «неверным ответом», расход — худшим случаем, а повтор шёл с теми же настройками и снова обрывался.
- Клиент теперь вызывает `messages.create` и сам разбирает ответ той же схемой: сначала `stop_reason`, потом JSON. Обрезка распознаётся как `truncated` с реальным расходом.
- После обрезки — **одна** попытка с настройками `on_truncation` этапа (`config/llm.yaml`: для C `effort: low`, `max_output_tokens: 12000`; для B `low`, `5000`) и просьбой отвечать короче. Настройки сохраняются до конца анализа компании. Вторая обрезка — анализ завершается ошибкой. Без `on_truncation` повтора нет. Одинаковый запрос никогда не повторяется.
- Каждая попытка проходит проверку бюджета по своему лимиту токенов; худший случай в `--dry-run` считается по наибольшему лимиту.

### 2. Сначала email
- Основной канал обращения — публичный email на сайте: на домене компании или в публичной почте (gmail и т. п.), с источником, MX-проверкой и риском адреса. Форма — запасной канал, её заполняет только человек.
- Без email компания помечается «нужен ручной поиск контакта» (досье, отчёт кандидатов, CSV `email_contact`, строка `npm run deep`). Подсказки: адрес из прошлой проверки, адрес, скрытый защитой от сбора (Cloudflare), — его код не расшифровывает, смотреть вручную в браузере.
- Коммерческий потенциал, доступность контакта и риск обращения по-прежнему отдельны. Адреса не придумываются и не угадываются. Сбор телефонов не менялся.

### 3. Согласованность рекомендации
- Модель называет, что мешает `pursue` (`recommendation_blockers`: нет факта, неясная значимость, проблема не видна, уже есть, ничего не подтверждено, не наш клиент, неизвестные внутренние показатели).
- Код сверяет их с решением и доказательствами: `maybe` только из-за неизвестных показателей (или без причины), `drop` без оправдывающей причины, «нет факта» при наличии факта, `pursue` с названными препятствиями — противоречие. Модель получает одну попытку исправить (в пределах существующих повторов).
- Код рекомендацию не повышает и по ключевым словам не меняет. Если противоречие осталось, оно показано в досье для человека.

### 4. Мелкое форматирование — без платного повтора
- «!» сразу после приветствия («Здравствуйте!», «Hello team!») код заменяет на «.» (или «,» перед переносом строки в en/nl) и проверяет письмо как обычно. Любой другой «!» и весь текст письма не трогаются; опора на доказательства проверяется как раньше; черновик всегда читает человек.

## 2026-10-25 — Этап C: ремонт черновика вместо повторного анализа

Проверочный запуск A1 Designs (2 вызова, $0.0101): анализ был верным, но в теме письма 8 слов вместо 7 — и ради этого заново генерировалось всё досье (12,5 тыс. входных токенов, 8 тыс. выходных), а этот повтор оборвался. Решения Claude Code; оператор принимает их при ревью PR #2.

### 1. Проверка анализа отдельно от проверки письма
- Полный повтор запускают только проблемы анализа (цитаты, находки, признаки сайта, выбор предложения, согласованность рекомендации, язык). Проблемы только письма (правила текста, опора на доказательства) полный повтор больше не запускают. Если полный повтор всё же нужен, ему передаются и замечания к письму.
- Безопасные механические правки — локально, без запроса: «!» после приветствия, строка отказа, написанная моделью (её добавляет код).
- Остальные проблемы письма — **один** небольшой запрос ремонта (`llm.stages.deep.draft_repair`: `effort: low`, до 2 000 токенов), который генерирует только письмо. Ему передаются выбранное предложение и его проверенные утверждения с метками (факт/вывод/…), прежнее письмо и замечания кода — без текста сайта. Правила письма берутся из того же раздела промпта, что и в анализе.
- Исправленное письмо проходит те же проверки: правила текста, связь с выбранным предложением, факт можно назвать, о выводе только спросить. Не прошло — досье сохраняется как есть, письмо помечено непригодным с причиной.
- Ремонт не выполняется для «не предлагать» и когда нет обоснованного предложения. Сбой запроса или бюджет — ремонт пропускается без повторов и без потери досье.

### 2. Учёт стоимости
- Вызовы ремонта записываются в `llm_calls` с назначением `deep_draft` (анализ — `deep`). Досье, итоговая строка `npm run deep` и `--dry-run` показывают вызовы и стоимость анализа и ремонта отдельно; худший случай в `--dry-run` включает один ремонт на компанию.
- Изменение любого из двух промптов меняет версию промпта и сбрасывает кэш.

### 3. Расход токенов
- Видимый ответ модели — 5–7 тыс. символов (≈2–3 тыс. токенов) у всех компаний, а выход — 4,5–7,6 тыс. токенов: 40–65 % выхода — рассуждения модели при `effort: medium`, они сильно колеблются.
- Решено консервативно: `effort` остаётся `medium` (качество при `low` не проверено сравнением); базовый `max_output_tokens` 8 000 → 10 000 (A1 упиралась в 8 000 в 3 из 5 попыток; оплачиваются только использованные токены, обычная стоимость не растёт); в схеме ответа — ограничения длины списков. Восстановление после обрезки (`low`, 12 000) остаётся запасным путём.
- Переход на `effort: low` стоит решать по платному A/B-сравнению на тех же компаниях.

## 2026-10-25 — Лиды: сначала коммерческая возможность, а не дефекты сайта

Шорт-лист по техническим находкам оказался непригоден: битые ссылки, старый копирайт, PDF-каталоги и мобильная вёрстка — это мелкие правки, а не проекты, за которые бизнес заплатит. Решения Claude Code; оператор принимает их при ревью PR #2.

### 1. Что считается лидом
- Лид — это **проект, который можно продать**: B2B-каталог с запросом цены (КП), калькулятор или конфигуратор, онлайн-запись, кабинет клиента / статус заказа, обработка заявок и уведомления, интеграции с CRM/складом/учётом. Тип проекта определяется по предложениям этапов B и C, которые описывают процессы бизнеса (как клиент узнаёт цену, заказывает, записывается).
- Технические находки — **отдельная оценка качества сайта**. Сами по себе лид не дают при любом их количестве; предложение категории «исправление сайта» в оценку проекта не входит.

### 2. Модель квалификации (`src/leads/qualify.ts`, по сохранённым данным, без LLM)
- **Значимость для бизнеса** (0–3) — по оценке этапа B: коммерческая активность, размер (микробизнес −1). IT-компании, крупные сети, «skip» этапа B и «не предлагать» этапа C — исключаются с причиной.
- **Сила доказательства** (0–3) — факт этапа C = 3, вывод этапа C = 2; цитата этапа B = 1 (этап B проверяет только, что текст есть на сайте, а не что он подтверждает проблему); техническая находка как довод для бизнес-проекта = 1; вывод только из того, что «на сайте этого нет», = 1; не прошедшее проверку предложение этапа C — не выше 1.
- **Масштаб проекта** (1–3) — из оценки этапа C, иначе типичный для типа проекта.
- **Дублирование** — уже есть на сайте: проект не считается; частично есть: −1.
- **Отдельно и без влияния на ранг:** email (основной канал), юридический риск обращения, качество сайта.
- Группы: **сильные** (доказательство этапа C, значимость ≥ 2, масштаб ≥ 2, сумма ≥ 7), **проверить** (правдоподобный проект, но слабое доказательство, малый масштаб или бизнес не оценён), **только мелкие дефекты**, **исключить**.
- Код не делает выводов о потребности из отсутствия функции и не повышает оценки: предложения и вопросы берутся из сохранённых результатов этапов B/C с их метками.

### 3. Отчёт
- `npm run leads` — только чтение базы; `data/reports/leads-*.md` и `.csv`. Для каждого лида: что можно построить, почему это может быть важно (гипотезы), доказательства с метками и ссылками, что ещё проверить, следующий шаг, контакт, риск, качество сайта отдельно.
